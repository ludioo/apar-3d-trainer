# T3.1 audit dan hasil implementasi

28 Oktober 2026. **Acceptance T3.1 diterima Barkah.** Barkah mengonfirmasi sudah memeriksa dan menyatakan lolos, meminta task/checklist selesai, dokumen diperbarui serta commit/push ke develop. Angka audit AI tetap dipertahankan: target Performance >=85 dan APAR siap <3 detik belum tercapai pada pengujian lokal yang dilaporkan. Penutupan checklist berdasarkan acceptance pengguna, bukan audit numerik baru; rincian perangkat/angka pemeriksaan Barkah tidak diberikan. T3.2 tidak dimulai dan main tidak diubah.

## Metode

- Lighthouse 12.8.2, Chrome 156.0.0.0, mobile Slow 4G bawaan/simulasi; Node 22.14.0. Setiap run memakai Chrome profile baru dan reset/cache browser, tanpa ?debug. Baseline dan final masing-masing tiga run berurutan; pengukuran lain tidak dijalankan bersamaan.
- Server lokal `t3.1-server.cjs`: dist produksi, gzip HTML/JS/CSS, binary unchanged, Cache-Control no-store; sama sebelum/sesudah. Ini server alat QA, tidak menambah backend aplikasi. Kompresi/HTTP/cache deployment Vercel baru belum diverifikasi.
- Pengukuran APAR terpisah: 9 Mbps download, 1,5 Mbps upload, latency CDP 60ms, CPU slowdown 4×, viewport 412×823/DPR 1,75, mobile/touch. DPR renderer tetap dibatasi 1,5.
- Baseline diamati melalui draw model setelah response HDR selesai, splash opacity 0, lalu satu rAF; screenshot final ditinjau. Build final memakai mark `apar:visible`: environment sudah siap, model dikompilasi dan dirender, transisi splash selesai, lalu satu rAF. Probe silang berada sekitar 4ms setelah mark final. Waktu dilaporkan dari navigation time origin, bukan dari awal fetch atau load:done; LCP splash tidak dianggap waktu APAR.
- Transfer dihitung dari navigation transferSize + seluruh resource same-origin sampai model siap dan jaringan tenang selama 750ms, sebelum interaksi; response/header turut dihitung. Blob worker tidak merupakan transfer jaringan. Ukuran disk, decoded JS dan seluruh file dist tidak disamakan dengan transfer awal.
- Script `t3.1-audit.cjs` dan jalur alat lokal mendokumentasikan cara reproduksi. Gunakan nama stage baru agar tidak memakai ulang hasil Lighthouse yang sudah tersimpan. Reset Chrome tidak membuktikan cache driver GPU OS ikut kosong.

## Perubahan dan ukuran

- Model dipreload satu kali; gzip HDR dipreload satu kali pada browser yang mendukung DecompressionStream. Tanpa fasilitas tersebut preload langsung memilih HDR asli. Gzip hilang/rusak fallback ke asli; gagal seluruh HDR tetap memakai directional light dan tidak menghasilkan mark sukses `apar:visible`.
- HDR 1024×512 asli 1.615.248 byte menjadi gzip 1.187.546 byte, tanpa perubahan byte/piksel sesudah dekompresi. Sumber asli dipertahankan. Disk bertambah 1.187.546 byte, transfer HDR normal berkurang 427.702 byte. `npm run optimize:environment` dan build meregenerasi gzip; `npm run check` membandingkan byte, piksel, resolusi, tipe dan color space.
- PMREMGenerator/compileEquirectangularShader mempersiapkan environment menggunakan sumber yang sama. compileAsync model dilakukan sebelum render pertama. Scene/camera/renderer dan lifecycle fitur tetap; tidak menambah loop render.
- Seluruh HUD/marker/bridge debug dan stats bawaan three di satu chunk lazy: 3,00 KB mentah / 1,50 KB gzip. Tidak dimuat pada halaman biasa; gagal import tidak menghentikan aplikasi. Stats mengikuti render aktual, dapat mempertahankan tampilan terakhir saat idle, dan tidak membuat loop sendiri. Lisensi MIT disertakan di public/licenses/stats.txt; tanpa dependency baru.
- Bundle utama 818,28 KB / gzip 225,61 KB dibanding 817,71 KB / gzip 225,46 KB baseline; CSS 27,66 KB / gzip 5,28 KB dibanding 27,56 KB / gzip 5,26 KB. Warning bundle utama >500 KB existing tetap. Decoder default duplikat tetap berada di dist tetapi tidak diunduh; tidak dibersihkan karena tidak mengurangi transfer awal.
- GLB identik dengan HEAD, Git blob `43cf956321ab35d1b12f1affdfdaa2d8fa4153d4`. Mesh, atlas, tekstur WebP, pilihan warna/bracket, batas DPR, font, K3, localStorage dan versi dependency tidak diubah.

## Bottleneck dan usulan revisi rencana

Lighthouse final run kedua masih mencatat long task 3268ms berlabel Unattributable serta beberapa task JS 635/429/304ms. Pada 4G run tersebut, load-start sekitar 1,241s, environment-ready 3,166s, model-ready 3,280s dan visible 4,023s. Jadi mengurangi byte saja belum cukup; kerja startup, persiapan environment/model dan render awal masih mendominasi. Label Unattributable tidak membuktikan seluruh long task adalah PMREM; atribusi CPU/GPU lebih rinci diperlukan sebelum menjanjikan hasil.

Usulan revisi berikut **belum diimplementasikan**. Setelah Barkah menerima T3.1, usulan ini menjadi catatan opsional; tidak ada pekerjaan revisi yang berjalan atau otomatis diotorisasi:

1. Profilkan CPU/GPU startup dengan timing tahap HDR decode, PMREM, model decode, compile dan render pertama pada kondisi baseline yang sama. Gunakan hasil untuk mengonfirmasi porsi biaya yang bisa dipindahkan dari runtime.
2. Siapkan kandidat environment PMREM dari HDRI 1K existing menggunakan renderer three pada alat praproses lokal, simpan data half-float hasilnya dengan gzip lossless dan metadata ukuran/mapping. Pada aplikasi, muat sebagai DataTexture CubeUV agar jalur normal melewati konversi PMREM runtime; HDRI asli tetap fallback. Tidak memakai Blender, aset sumber baru atau menurunkan resolusi sumber. Verifikasi data dan perbandingan visual pada GPU yang sama sebelum mengganti jalur normal.
3. Pertahankan compileAsync, render on demand, profil pengujian dan batas kualitas. Jalankan kembali tiga run serta regresi/visual; jangan menyatakan target tercapai sebelum angka membuktikannya. Jika kandidat tidak setara secara visual atau bottleneck utama ternyata di tempat lain, bawa temuan itu kembali ke planning, bukan menurunkan kualitas diam-diam.
